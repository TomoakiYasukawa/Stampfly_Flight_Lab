# ロガーのグラフ表示修正

`stampfly_imu_monitor/StampFlyIMUApp.m` と比較し、グラフ更新処理は同じだった。今回の受信ログには BuildID 1401 と BuildID 2026101202 のデータが混在し、約9秒間で26回、機体時刻が逆戻りしていた。アプリはそのたびに履歴を消去していた。

ここでいう「混在」は、異なるプログラムのデータを同じ機体の連続した記録として扱っていた、という意味。データの時刻は各機器の起動からの経過秒なので、「対象プログラムの45秒 → 別プログラムの1870秒 → 対象プログラムの45秒」の順に届くと、従来のアプリは再起動と判断してグラフを消していた。

修正後の動作は次のとおり。

- `ExpectedBuildID=1401` のフレームだけを表示・記録する。対象外の数を表示する。
- 表示時刻を接続開始からの相対秒とし、機体再起動は履歴を残して線を区切る。保存される生タイムスタンプは維持する。
- 最新500点固定ではなく直近10秒を保持する。受信周期の違いで右端だけにならないようにする。
- 受信した複数フレームを処理し終えてから、X/Yデータをまとめて描画する。
- 既存の混在した保存ログも、履歴画面で対象ビルドを選別する。

検証では別ビルドの混入、25/50/400 Hz、再起動、部分受信、欠落・CRC、記録の対象選別を扱う。機体モデル・通信パケット・ファームウェアは変更しない。

実際の混在ログを対象ビルドで読むと、488点中461点が採用され、27点が対象外になった。表示期間は9.2秒、最大刻みは0.021秒、時刻逆戻りは0回になった。

独立したMATLABセッションで9項目すべてに合格した。結果は `logger_display_verification.json`。実機のUSB接続を使わず、既存のロガー接続を維持して検証した。開いたままMATLABがクラスの変更を反映した場合も、初回受信で追加した表示状態を初期化する。

接続中のアプリでも、加速度の各線に約10.02秒分の有限な502点が残り、時刻の逆戻りがないことを確認した。表示軸の幅は10秒で、受信フレーム数も増え続けている。

BuildIDはプログラムの種類・版を表す番号であり、機体固有の識別子ではない。今回の混在した2ビルドは区別できるが、同じビルドを搭載した複数機体を区別する仕組みは現在のパケットにない。別ビルドの具体的な送信機器はログだけでは特定できない。
