# 2026-10-17 水平補助版の落下・記録・Z速度の調査

**CPU1固定を維持したRevision 1804で、ユーザーから問題解消・安定飛行の報告を得ました。** 待機中のCPU0 idle watchdogを1802で捕捉し、CPU固定版1803の机上試験後、区間計測版1804を実装して実飛行しました。成功版のモデル・BINを保全しています。過去の落下時のwatchdog診断はなく、元の実飛行の直接原因を全件で確定したとは扱いません。

## Z速度で修正したこと

`AttitudeAltitudeEstimation/AltitudeKalman`へg基準の加速度を渡し、秒で積分していました。入口の **VerticalAccelGToMps2** で9.80665倍し、速度m/sに合う単位へそろえました。内部バイアスもm/s²になり、従来ログのg列へは **KalmanBiasMps2ToG** で戻します。

また、待機中は内部状態を保持しながら共分散を毎周期100Iへ戻していました。ToFの量子化による小さな変化が速度へ強く反映され、飛行切替時の偽速度が再現しました。**PreviousParkingReset → NOT → ParkingResetEdge** により、待機へ入る立上りだけリセットします。Kalman本体、7 PIDの係数、Supervisorは維持しています。

| 機器I/Oを含まない実ブロック試験 | 結果 |
|---|---:|
| 静止・量子化ToF・待機→飛行の速度ピーク | 旧0.213357 → 修正0.008364 m/s |
| 既知の滑らかな上昇に対する速度RMSE | 0.011199 m/s |
| 停止後の再離陸切替 | 合格 |

[高度境界の検証](../../vertical_boundary_verification.json)と[変更範囲の照合](../../incident_invariants_verification.json)に判定を保存しました。修正により高度制御入力は変わるため、旧版との全制御出力一致は主張しません。

**残る制約：** 高度推定には機体Z加速度とToF斜距離を使っています。姿勢からの鉛直加速度投影と、高度制御用ToFの傾き補正は未実装です。傾斜中の推定速度を地面に対する厳密な鉛直速度とは扱えません。アプリのToF鉛直投影・直前0.25秒の高度変化率は比較用で、独立した速度真値ではありません。

## 自動記録と表示を修正したこと

機体の公式状態は **0=初期化、1=800サンプル校正、2=飛行制御、3=待機、5=自動着陸** です。アプリが別の状態定義を使っていたため、着陸・ホバリングの開始線が実際の浮上と一致しませんでした。Mode 2はモーター立上げからの制御区間であり、ホバリング開始ではありません。

- Mode 2/5で自動開始し、直前2秒と待機復帰後1秒を保存。次の飛行は別ファイルへ記録します。
- 待機復帰、通信途絶、初期化復帰、機体時刻リセット、手動停止・切断を別の終了理由として保存します。
- 時刻の大きな逆転は複数の進行パケットで確認します。単独の遅延・重複パケットは起動をやり直したと扱いません。
- CRC正常データは表示採用条件の外で記録し、表示しなかった遅延値も生データに残します。新起動の補足値を前飛行へ混ぜません。
- 履歴は飛行制御開始を0秒、直前区間を負値で表示。欠測・再起動を線でつなぎません。旧Raw/Filtered速度列は同じKalman値のため、別の速度フィルターとして重ねて表示しません。

[自動記録・履歴・表示の48試験](../../incident_recording_verification.json)は全件合格しました。無線で受信できなかったデータを復元する機能ではありません。

旧3記録の新版履歴でも、待機→飛行制御、負の直前時刻、時刻リセット終了を照合しました。画面キャプチャ用ツールは接続できず、画像書き出しも更新が不完全だったため、アプリの目視確認完了とは扱っていません。状態ラベル、集計、プロット値の検証と画像による確認を区別しています。

[配布コピーの検証](../../imu_distribution_verification.json)では、既定のMATLABパスから別フォルダーのプロジェクトを開き、機体・受信機モデルの更新とアプリの起動・終了を確認しました。独自コードはすべてコピー内へ解決し、検証したモデル・アプリのSHA-256を保存しています。元プロジェクトの登録・全12項目のチェックも合格しました。

## 待機中のwatchdogを捕捉した結果

1802はESP32の起動理由、両CPUのidle経過時間、制御タスクの最小残りスタック、空きheapを観測します。USB未接続時にUSB書き込みを避け、接続中も部分書き込みの再試行を最大20 msへ制限しました。ウォッチドッグは無効化していません。

1802のUSB取得中、**Mode 3・PWM 0の待機状態で**次のESP32診断を保存しました。

```text
task_wdt: Task watchdog got triggered.
 - IDLE0 (CPU 0)
CPU 0: Baserate
CPU 1: IDLE1
ELF file SHA256: 55c3f5728
Rebooting...
```

対応するELFのSHA-256を照合してバックトレースを解読しました。呼出し経路は`delayMicroseconds → flow_read_burst → pmw3901_logger_step → StampFly_IMU400_step → Baserate`です。これは停止時点の実行箇所であり、光学フロー関数が永久に停止した証拠ではありません。待機中の自動再起動は確認できましたが、過去の実飛行の落下が同じ原因だったとはまだ断定していません。[watchdog原文・ELF・解読結果](20261017_waiting_watchdog.json)

## CPU固定版1803の確認範囲

タスク生成時からBaserateをCPU1へ固定しました。従来はCPU未固定のタスクが最初の浮動小数点演算の時点でCPUに固定され、1802では再起動前にCPU0、再起動後にCPU1で実行されていました。CPU0の無線・I2C・USB処理と制御タスクを分離します。またidleの更新時刻を現在時刻より先に読み、CPU間の更新競合による符号なし減算の周回を解消しました。[設定箇所](../../cpu_tasks.md)

| USBのみ・水平固定・プロペラなし | 90秒待機 | 約18秒のMode 2を含む取得 |
|---|---:|---:|
| 自動再起動・CRCエラー | 0・0 | 0・0 |
| BaserateのCPU | 1 | 1 |
| CPU0 idle経過の最大 | 775 µs | 1,161 µs |
| 記録した全タスク周期数 | 36,000 | 27,200 |
| 2.5 ms超過 | 5,730回 | 7,912回 |
| 全タスク最大 | 3.524 ms | 3.790 ms |
| タイマー取りこぼし累計最大 | 0 | 109 |

右列の周期数・超過数はMode 2だけでなく、前後の待機・自動着陸を含む取得区間です。Mode 2中の平均は約2.50 msで、処理時間の余裕不足が残っています。磁気センサーの更新は継続し、静止Z速度も小さい範囲でした。試験後はMode 3・PWM 0への復帰を確認しました。[待機の集計](../../runtime1803_waiting_verification.json)、[Mode 2の集計](../../runtime1803_mode2_verification.json)

既存SDKのidle watchdog監視はCPU0のみで、CPU1のidle監視は無効です。ウォッチドッグ設定は変更していません。CPU1へ移して再起動しないことだけで、周期余裕や飛行安定性の解決とは扱いません。電池なしの電圧・PWM飽和は実飛行条件の値として評価していません。

取得ヘルパーがMode 5の正常受信中にも`MODE2_TELEMETRY_LOSS_CAPTURED`と表示して終了する不具合を確認しました。「最後のMode 2からの時間」を誤って通信途絶と扱っていたためです。保存ログでは受信が継続しており、この表示を機体の停止証拠とは扱いません。次の取得では、CRC正常パケットが届かない時間を判定します。

## 処理時間の切り分け

1803の`SFTIMING`はモデル内の計測点までで、`SFTASK`はstep全体です。平均で約0.5 msの処理が計測点の後にあり、50 Hzの記録用距離換算、状態表示、状態更新などを含みます。区間計測版1804では既存外部関数の入口・出口をリンカーで挟み、同じ引数・戻り値を通して計測します。制御式・7 PID・Supervisor・14 MATLAB Function本文は維持しました。区間時間には割込みと他タスクによる待ちも含まれます。

30秒のUSB待機取得では平均step約2.29 ms、IMU読み出し約0.29 ms、光学フロー読み出し約0.32 ms、姿勢推定等の区間約0.85 msでした。毎秒の診断出力は最大約1.31 msの一時負荷があります。[区間の集計](../../runtime1804_sections_waiting.json)、[待機の集計](../../runtime1804_waiting_verification.json)。実飛行成功後はこの版を保全し、追加の負荷低減は別の変更として扱います。
